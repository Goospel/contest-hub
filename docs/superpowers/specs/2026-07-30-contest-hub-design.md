# contest-hub 설계 (2026-07-30)

인터넷에 흩어진 공모전을 자동으로 모아 한곳에서 보여주는 공개 웹사이트.

## 배경

사용자는 그동안 인스타그램 광고로만 공모전을 접했고, 공모전 전문 사이트(위비티·씽굿 등)의 존재를 몰랐다. 그래서 처음 구상은 "LLM에게 검색시켜 찾아오게 한다"였다.

초안에서는 애그리게이터(위비티)를 크롤링해 볼륨을 채우고 LLM 웹검색으로 롱테일을 보태는 하이브리드로 잡았다. **이 전제는 조사 후 폐기했다.** 사용자의 원래 구상이 결과적으로 옳았다.

### 왜 애그리게이터를 긁지 않는가

`robots.txt` 는 위비티·씽굿·링커리어·콘테스트코리아 모두 목록 페이지를 허용한다. 막는 건 그쪽이 아니다.

- **이용약관**: 위비티 제9조는 서비스에 게시된 자료의 지적재산권이 위비티에 있다고 명시하고, 이용자가 서비스에서 얻은 정보를 가공·판매하는 등 상업적으로 이용하는 것을 금지한다. 우리가 하려던 것이 정확히 "목록을 긁어 가공해 자체 사이트에 게시"다. "상업적으로"라는 한정 때문에 비영리라면 해당하지 않는다고 볼 여지는 있으나, 나중에 광고를 붙이면 즉시 위반이 된다.
- **저작권법상 데이터베이스제작자의 권리**: 개별 사실(공모전명·마감일·주최)은 저작권 대상이 아니지만, 상당한 투자로 구축한 데이터베이스는 별도 보호를 받는다. 애그리게이터의 목록을 체계적으로 복제해 **같은 성격의 애그리게이터를 만드는 것**은 그 권리 침해의 전형적 형태이며, 비영리라고 면제되지 않는다.

법률 판단이 필요한 영역이라 단정하지 않는다. 다만 이 리스크를 감수할 이유가 없다 — 아래 대안이 오히려 더 나은 데이터를 만든다.

### 왜 원출처인가

공모전 정보는 주최 측이 **널리 알려지길 원하는** 정보다. 원출처에서 모으면 법적으로 깨끗하고, 애그리게이터에 등록조차 안 된 공모전(사용자가 인스타에서 보던 바로 그런 것들)까지 잡힌다.

문제는 원출처가 흩어져 있다는 것이다. 조사 결과 **"모집 중인 공모전"을 통합 제공하는 공공 API는 존재하지 않는다.**

| 후보 | 판정 |
|---|---|
| KIPRISPlus 공모전 아이디어 API | 과거 **수상작** DB. 모집 중인 공모전이 아니다 |
| 한국산업인력공단 해외인턴 공모전 | 범위가 해외인턴 하나로 지나치게 좁다 |
| 한국콘텐츠진흥원 지원사업공고 | 인접 영역. 유일하게 검토할 만한 후보 |
| bizinfo 지원사업정보 | 기업 지원사업이라 결이 다르다 |

기관별 공고 페이지를 개별 크롤링하는 것은 기관 수만큼 파서가 필요해 비현실적이다.

## 수집 전략 — 발견자와 승격

**LLM 웹검색이 주력이다.** 그리고 검색이 반복해서 물어오는 도메인은 전용 소스로 승격시킨다.

```
LLM 웹검색 (발견자)
   │  매일 질의 5개 → 원출처 URL 확보
   │
   ├─ 그때그때 수집 → verify() → DB
   │
   └─ 같은 도메인이 반복 등장
          ↓
      전용 소스로 승격 (sources/ 에 파일 하나)
          ↓
      그 도메인의 공고 목록을 직접·전량 수집
```

승격 대상은 **주최기관 본인의 공고 페이지**다. 애그리게이터가 아니므로 위의 법적 문제가 없다.

이 구조의 성질:

- **처음엔 얇고, 쓸수록 두꺼워진다.** 초기 데이터는 수십 건 수준에서 시작한다. 이건 감수하는 비용이다.
- **승격은 수동 판단이다.** 도메인 빈도를 자동 집계해 자동으로 파서를 만들 수는 없다. `contests.source_url` 을 도메인별로 집계하는 SQL 한 방이면 후보가 보이고, 파서를 쓸지는 사람이 정한다. 별도 추적 테이블을 두지 않는다.
- **소스 인터페이스가 이미 플러그인**이라 승격 비용이 파일 하나다.

## 범위

### 1차 (이번 구현)
수집 → DB → 목록/검색/필터 → Vercel 배포.

### 보류 (v2)
회원/로그인, 관심 공모전 저장, 마감 알림, 관리자 검수 화면.

## 데이터 모델

테이블 하나로 간다. 소스별 테이블 분리는 지금 필요 없고 `source` 컬럼으로 충분하다.

```
contests
  id            serial primary key
  source        text      -- 'llm-search' | 승격된 소스 이름
  source_url    text not null
  title         text not null
  organizer     text
  category      text[]    -- 정규화된 분야 태그
  target        text      -- 응모 대상 (대학생, 일반인 등)
  prize         text      -- 총상금 원문 텍스트
  description   text
  thumbnail_url text
  starts_at     date
  deadline      date
  dedupe_key    text unique not null  -- 정규화 제목 + 마감일
  status        text not null         -- 'published' | 'pending' | 'expired'
  first_seen_at timestamptz not null
  updated_at    timestamptz not null
  verified_at   timestamptz
```

**`dedupe_key`**: 제목에서 공백·특수문자·괄호를 제거하고 소문자화한 값 + `deadline`. 같은 공모전이 두 소스에서 들어와도 한 행으로 합쳐진다.

**unique 제약은 `dedupe_key` 하나만 건다.** `source_url` 에도 unique를 걸면 같은 공모전을 두 소스가 서로 다른 URL로 가져왔을 때 upsert가 깨진다 — `dedupe_key` 로 기존 행을 찾아 `source_url` 을 덮어쓰려는 순간 그 URL이 다른 행에 이미 있으면 제약 위반이 난다. 동일성의 단일 출처는 `dedupe_key` 다.

**`category`** — 분야 태그. 구현: `lib/categories.ts` (테스트 20건).

**다중 선택이다.** 한 공모전이 "디자인 + 영상"일 수 있고 억지로 하나를 고르지 않는다. DB에는 `slug` 만 저장하고 한글 표시명은 코드 상수로 둔다 — 표시명을 바꿔도 데이터를 건드리지 않는다.

| slug | 표시명 | | slug | 표시명 |
|---|---|---|---|---|
| `design` | 디자인 | | `it-dev` | IT·개발 |
| `video-photo` | 영상·사진 | | `startup` | 창업·비즈니스 |
| `idea` | 아이디어·기획 | | `content-character` | 콘텐츠·캐릭터 |
| `naming` | 네이밍·슬로건 | | `science-eng` | 과학·공학 |
| `writing` | 글·문학 | | `other` | 기타 |
| `art-craft` | 미술·공예 | | | |
| `music-performance` | 음악·공연 | | | |

선언 순서가 곧 표시 순서이고 매핑 결과도 이 순서를 따른다 — 입력 순서가 달라도 같은 공모전이면 같은 태그 배열이 나온다.

**키워드 선정 원칙** (LLM의 자유 텍스트를 이 집합에 매핑한다)

- 한두 글자 한글은 넣지 않는다. `시` 는 `전시`·`시나리오` 에 묻어간다
- 다른 분야의 키워드를 부분 문자열로 포함하면 안 된다. `웹` 은 `웹툰` 에 걸린다
- 영문 키워드는 **단어 경계를 요구한다**. 없으면 `ui` 가 `guide` 에, `ai` 가 `chain`·`thai`·`aid` 에 묻어간다
- 애매하면 넣지 않는다. 놓친 건 `other` 로 가고, **`other` 가 쌓이면 그게 키워드 보강 신호다.** 잘못 붙은 태그는 그런 신호를 주지 않는다

`other` 는 매칭 대상이 아니라 아무것도 안 맞을 때의 결과다. 이 빠져나갈 구멍이 없으면 LLM이 안 맞는 것을 억지로 가까운 태그에 밀어넣어 나머지 태그의 정확도까지 갉는다.

**`status`**
- `published` — 공개.
- `pending` — 검증 실패. 목록에 안 나온다.
- `expired` — 마감 지남. 기본 목록에서 숨기되 토글로 볼 수 있다.

## 수집 파이프라인

소스는 플러그인이다. 소스 추가 = `sources/` 에 파일 하나 추가, 나머지 단계는 건드리지 않는다.

```
Source.collect() → RawContest[]
   ├ llmSearch      AI SDK generateObject + 웹검색  (주력)
   └ <승격된 소스>   cheerio 또는 공공 API           (성장분)
        ↓
   normalize()  날짜 파싱, 분야 태그 매핑, 필드 트림, dedupe_key 생성
        ↓
   verify()     needsVerification 인 소스만
        ↓
   upsert by dedupe_key
```

### Source 인터페이스

```ts
interface Source {
  name: string
  collect(): Promise<RawContest[]>
  needsVerification: boolean
}
```

정의: `lib/types.ts`.

### normalize() — 날것을 DB 형태로

구현: `lib/normalize.ts` (테스트 44건).

**건 전체를 버리는 것은 제목과 원문 URL이 없을 때뿐이다.** 나머지는 읽지 못하면 null로 두고 통과시킨다 — 마감일이 없으면 `verify()` 가 `pending` 으로 보내고, 썸네일이 이상하면 그것만 버린다. 한 필드가 이상하다고 공모전 전체를 날리지 않는다.

**날짜 파싱.** 원문 표기(`2026.8.31`·`2026년 8월 31일`·`2026.08.31(금)`)를 ISO로 바꾼다. `verify()` 와 같은 원칙으로 **연도를 반드시 요구한다**. 두 자리 연도(`26.8.31`)도 거부한다 — 2026인지 1926인지 확정할 수 없다.

기간이 통째로 들어오면(`2026.08.01 ~ 2026.08.31`) **마지막 날짜를 마감으로 본다**. 단 마지막이 실재하지 않는 날짜면 그 앞을 본다. 한계: `2026.08.01 ~ 09.30` 처럼 뒤쪽 연도가 생략된 기간은 앞의 08.01을 집는다 — 연도 없는 조각을 앞 날짜의 연도로 채우는 추론은 하지 않는다.

**URL 스킴 제한.** `source_url` 과 `thumbnail_url` 은 `http(s)` 만 통과시킨다. 이 값들은 화면에서 원문 링크로 그대로 렌더되므로 `javascript:` · `data:` 가 섞이면 그대로 실행 경로가 된다. LLM 산출물을 신뢰하지 않는다는 원칙이 여기에도 적용된다.

### LLM 검색 소스 — 확정된 형태

프로브로 실측해 확정했다 (`scripts/probe-gateway.mts`, `scripts/probe-search.mts`).

AI Gateway는 웹검색을 두 갈래로 제공한다.

- **프로바이더 무관** — `gateway.tools.perplexitySearch()` / `exaSearch()` / `parallelSearch()`. 어떤 모델과도 조합된다. 요금은 게이트웨이가 청구한다 (Perplexity·Parallel $5, Exa $7 / 1,000 요청)
- **프로바이더 전용** — `anthropic.tools.webSearch_20250305()` 등. 해당 프로바이더 모델에서만 동작한다

**프로바이더 무관 쪽을 쓴다.** 모델을 바꿔도 검색이 따라오지 않아야 하고, `perplexitySearch` 는 `country`·`searchLanguageFilter`·`searchDomainFilter` 를 지원해 한국어 공고로 좁히기 좋다.

구조화 출력은 `generateObject` 가 아니라 **`generateText` + `output: Output.object({schema})`** 로 받는다. `generateObject` 는 도구 호출과 함께 쓸 수 없다. 구조화 출력 생성이 스텝 하나를 더 먹으므로 `stopWhen: isStepCount(N)` 에 검색 스텝 + 1 이상을 준다.

```ts
const { output } = await generateText({
  model: "anthropic/claude-sonnet-5",
  tools: { web_search: gateway.tools.perplexitySearch({ maxResults: 10 }) },
  output: Output.object({ schema }),
  stopWhen: isStepCount(6),
  prompt: /* ... */,
})
```

⚠️ **AI Gateway는 카드 등록 없이는 추론 호출이 403이다.** 인증(OIDC)과 결제 자격을 따로 검사해서, 모델 목록 조회는 되면서 추론만 막힌다 ([T-004](../../../claude-docs/troubleshooting/T-004.md)).

### verify() — 환각 방어

LLM 검색이 주력이 되면서 이 단계의 중요도가 올라갔다. LLM이 찾아온 건은 다음을 모두 통과해야 `published` 가 된다. 구현: `lib/verify.ts` (테스트 19건).

1. `deadline` 이 있다. 없으면 네트워크를 쓰지 않고 즉시 실패시킨다 — 마감일은 이 사이트의 핵심 정보이고, LLM이 찾지 못했다면 그 건 자체를 믿을 수 없다.
2. `source_url` 이 HTTP 200으로 응답한다.
3. 응답 본문에 그 `deadline` 이 실제로 등장한다.

**날짜 표기 매칭 규칙.** 한국 공고는 같은 날짜를 `2026-08-31`·`2026.08.31`·`2026. 8. 31.`·`2026년 8월 31일`·`2026/08/31` 로 제각기 쓴다. 구분자(`-` `.` `/` `년` `월`)와 0 생략을 유연하게 받되 **연도는 반드시 요구한다** — `8월 31일` 만 보고 통과시키면 다른 해의 같은 날짜 공고가 그대로 통과한다. 숫자열 경계(`(?<!\d)` / `(?!\d)`)를 둬서 긴 숫자 안에 우연히 포함된 경우를 배제한다.

이 규칙은 정상 건을 `pending` 으로 보낼 수 있다(false negative). 그 방향을 택한 이유는 `pending` 이 안전한 실패이기 때문이다 — 공개되지 않을 뿐 데이터는 남는다. 반대 방향의 실패(환각이 `published` 로 나감)는 사이트의 신뢰를 직접 깎는다.

실패 사유는 버리지 않고 남긴다: `no-deadline` / `http-error`(+상태코드) / `fetch-failed`(+메시지) / `deadline-not-found`. `pending` 이 쌓였을 때 원인별로 볼 수 있어야 규칙을 조정할 수 있다.

승격된 소스는 공고 페이지에서 직접 뽑은 값이므로 `needsVerification: false` 다.

### 충돌 규칙

같은 `dedupe_key` 가 이미 있으면 **승격된 소스가 LLM 검색을 이긴다**. 승격 소스의 값은 공고 원문 그대로이고 LLM 값은 요약·재구성을 거쳤기 때문이다. 같은 소스끼리 충돌하면 나중 값으로 갱신한다.

## 실행

`/api/cron/ingest` 를 Vercel Cron으로 **하루 1회**.

- LLM 검색: 매일 질의 **5개**. 질의문은 코드에 상수로 두고 손으로 조정한다 (예: "2026년 대학생 공모전 모집", "기업 디자인 공모전 접수중"). 비용이 여기서 결정되므로 자동 확장하지 않는다
- 승격된 소스: 매일 전량 순회
- 같은 잡에서 `deadline < 오늘` 인 건을 `expired` 처리

### 수집 예의

승격된 도메인을 읽을 때는 그 사이트의 `robots.txt` 를 먼저 확인하고 요청 간격을 3초 이상 둔다. 위비티가 `GPTBot` 에 `Crawl-delay: 3` 을 거는 것을 봤는데, AI 도구 트래픽에 대한 사이트 운영자들의 기대치로 읽고 이 값을 기본으로 삼는다. User-Agent에는 연락 가능한 식별자를 넣는다.

## 화면 (1차)

| 경로 | 내용 |
|---|---|
| `/` | 카드 그리드 목록. 기본 정렬 **마감 임박순**. 검색(제목·주최), 분야 필터, 마감 지난 것 보기 토글. 페이지네이션 |
| `/contest/[id]` | 상세. 원문 링크 버튼이 주 역할 |

무한스크롤 대신 페이지네이션을 쓴다 — 서버 컴포넌트에서 쿼리 파라미터로 끝나고 클라이언트 상태가 필요 없다.

**데이터가 적은 초기 상태를 전제로 만든다.** 빈 목록과 소수 결과가 초라해 보이지 않아야 한다.

## 테스트

정규화·중복제거·날짜 파싱·검증 로직에 테스트를 **먼저** 쓴다.

- `buildDedupeKey` — 완료 (7건)
- `verify()` 는 fetch를 주입받게 만들어 네트워크 없이 테스트한다
- 승격 소스의 파서는 실제 공고 페이지 HTML을 픽스처로 저장해 테스트한다
- 테스트에서 실제 네트워크를 타지 않는다

UI는 테스트하지 않는다. 목록 렌더링에 회귀 테스트를 붙일 만큼의 로직이 없다.
